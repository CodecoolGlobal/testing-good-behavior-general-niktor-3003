## Overall assessment

The application supports the main exploration flow: locations load,
encounters display an opponent, players can select an owned Pokémon, and
they can leave an encounter before fighting. Manual testing also observed
a successful capture after victory and a stopped battle after defeat.

The application does not yet meet all assessed requirements. The location
list does not reappear after either observed battle outcome (BUG-001), and
the no-encounter message differs from the specified text (BUG-002).
The core flow is usable in the observed cases, but these findings and the
coverage limits below prevent a conclusion of full requirement compliance.

## Findings and recommended priorities

1. [BUG-001: Location list missing after victory or defeat](bug-reports/BUG-001-locations-not-shown-after-victory.md).
   Restore the required post-battle transition and retest both outcomes.
   This affects the expected game flow and should be addressed before
   the text discrepancy.
2. [BUG-002: No-encounter message text](bug-reports/BUG-002-no-encounter-message-text.md).
   Align the message with requirement 2.3 and rerun the exact-text scenario.
   The current message communicates the state and its Back navigation works.
3. [IMP-001: Display owned Pokémon statistics](improvements/IMP-001-player-pokemon-statistics.md).
   Consider showing HP, Attack and Defense before battle so players can
   compare options. This is a usability suggestion rather than an explicit
   requirement violation.
4. Review the observed Showdown GIF usage against the requested
   `front_default` sprite source.

## Risks and limitations

- One earlier UI run timed out waiting for the `spring-path` message while
  another scenario at that location passed. The final run reached the
  expected text assertion; the earlier timeout remains unexplained.
  Failure screenshots are now collected to support future investigation.
- Opponents and damage are random, and the UI depends on external PokéAPI
  responses. The tests do not control these data sources or network timing.
- Manual battle coverage consists of the recorded examples, not repeated
  coverage of every opponent, owned Pokémon or outcome combination.
- API coverage is limited to two GET endpoints. Mutating requests, input
  validation, duplicate capture behavior and persistence boundaries are
  not tested by the API scenarios.
- URL checks validate the returned entry type and prefix; they do not
  fetch each URL or establish that every referenced Pokémon exists.
- Cross-browser, mobile, accessibility, load and security testing were
  outside this exercise's tested scope.
- The actual exploratory testing duration was not recorded. Completion
  of the assignment's 2–3 hour timebox cannot be confirmed from these notes.
